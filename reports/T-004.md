### Decisions I made
- Manifest link injected over http(s) only: on `file://` Chrome logs a CORS error fetching a manifest, which would break AC-4.
- Pinch-zoom is left on (spec asks only for no double-tap zoom; blocking pinch hurts accessibility).
- Saved colours are applied at start, so the title shows them on the first screen (as after choosing colours in a session).
- Settings are saved when a game starts (the moment a full set of choices is in use).

## Round 1 addendum (2026-09-27): independent review, after the status change
I ran two independent multi-agent reviews of f4ddbb4 (3 reviewers each, with different lenses: spec, iPhone/PWA/service worker, regressions and house rules). Every finding was then checked by a separate agent told to refute it. I changed code only for confirmed findings that fall inside T-004. Status stays `IN REVIEW`; please review up to 560f138.

Commits:
- d802314 T-004: key the offline cache without the query string
- 560f138 T-004: update comments that still described settings as in-memory only

### What changed
- **sw.js bug fixed (confirmed by both reviews).** The fetch handler read with `ignoreSearch` but wrote under the full URL. After one visit to a link with a query string (e.g. `?utm=` or `?fbclid=` on a shared link), Chrome's cache order made that copy the one served on every later launch, while only the plain `/TTT/` entry kept being refreshed, so releases stopped arriving (AC-3, scope 2). Now one key without the query is used to read, fetch and write. Re-tested in a simulated worker with spec/Chromium cache ordering. Old code: after a shared-link visit, launches 2 and 3 after a release still served the old page. Fixed code: the release arrived on launch 2 and no extra cache entries were left. Offline, with or without a query string, still served the page.
- Three comments still called mode and colours "in memory only" or "per session"; they now mention `loadSettings()`.

### Corrections to Round 1
- **AC-11 / QA note was understated.** `qa/ui-check.js` doesn't just fail "AC-14 2P picker step X". Its next line clicks `#swatches .swatch`, which is never rendered because saved colours skip the picker, so Playwright waits 30 s and the script exits with `SCRIPT ERROR` **before printing any results**. Suggested fix on your side (qa/ is yours): open the 2P page in a fresh `browser.newContext()`, or clear localStorage and reload before its flow. AC-11 stays ticked on my ported run, but your script needs this change before it can confirm it.
- **Home Screen app storage (for the CEO's test):** on iPhone, the installed app doesn't share Safari's storage or service worker. After installing, open the app once while online before testing offline, and expect settings chosen in Safari not to carry over.

### Findings checked and rejected (no change)
- Precache (`addAll`) could store a redirected response. Not on GitHub Pages at `/TTT/`; the runtime path already refuses redirects.
- A Cache Storage failure on a cache miss would fail the request. Unrealistic in practice.

### Suggestions (not built)
- **Bug found by the review, older than T-001, not part of T-004: after any win, later boards shake instead of dropping in.** `shakeBoard()` leaves the `shake` class on `#board`, and `launchBoard()` only resets `drop`. `.board.shake` comes later in the CSS than `.board.drop`, so it wins. Confirmed in the browser: after a win, the next board has classes `board shake drop` and only `boardShake` runs. The drop is one of the protected animations. The fix is one line: `boardEl.classList.remove('drop', 'shake')` in `launchBoard()`. I suggest a small task for it.
